**工具**由你选择：matplotlib、graphviz、mermaid、SVG 转 PNG、draw.io 均可，

### 逐图内容要求

**图 1　整体系统架构**

必须体现：
- 顶部是浏览器（原生 JS + CSS，无构建步骤）
- 中间是 CloudBase 网关，向下分出两条独立链路
- 业务链路：云函数 `yard-api`（Event）→ PostgreSQL
- AI 链路：云函数 `ai-stream`（HTTP，SSE）→ 对话模型 / 向量模型 / 视觉模型
- 数据层：PostgreSQL（含 pgvector 扩展）+ 对象存储
- **两条链路要画成相互独立**，体现"AI 异常不影响业务请求"

**图 2　AI 请求链路与降级路径**

必须体现（这是一个含三个分支的流程图）：
- 主链路：访客提问 → 解析模型 Key
- 分支一（无 Key）：进入演示模式，返回内置示例回复
- 分支二（有 Key）：进入工具循环（最多三轮）→ 模型作答（SSE 流式）
- 分支三（模型不支持工具调用）：退回档案注入模式，不再调用工具
- 分支标签要清楚，连线不要交叉

**图 3　Agent 工具调用时序**

四泳道时序图：访客 / ai-stream / 对话模型 / 数据库。
消息顺序（实测一次真实调用）：
1. 访客 → ai-stream：提问
2. ai-stream → 对话模型：携带工具清单请求
3. 对话模型 → ai-stream：返回 4 个 tool_calls
4. ai-stream → 数据库：执行查询（经特权通道）
5. 数据库 → ai-stream：返回检索结果
6. ai-stream → 对话模型：带上结果再次请求
7. 对话模型 → ai-stream：生成最终回答
8. ai-stream → 访客：SSE 流式下发

底部标注实测调用的四个工具名：
`search_pets` → `check_requirement_gaps` → `get_pet_profile` → `get_adoption_policy`
并注明：三轮为上限，最后一轮不再提供工具。

**图 4　数据访问的两条通道**

必须体现：
- 通道一：前端 → CloudBase 网关 → 数据库，**受 RLS 策略约束**
- 通道二：云函数 → 腾讯云 OpenAPI（ExecutePGSql）→ 数据库，**以表属主身份运行，绕过 RLS**
- 明确标出哪些表只能走通道二：`applications`、`yard_administrators`、
  `yard_settings`、`knowledge_chunks`、`pet_photo_vectors`
- 这张图要能说明一个真实缺陷：云函数内部误用了匿名身份的数据库客户端，
  导致后台多个功能长期不可用

**图 5　RAG 检索与按需重建索引**

必须体现两条流：
- **写入流**：宠物档案 / 领养要求 / 领养政策 / 回访记录 → 按字段切块 → 批量向量化
  → 存入 `knowledge_chunks`（1024 维，HNSW 余弦索引）
- **查询流**：访客提问 → 向量化 → pgvector 余弦检索取 Top-K → 相似度阈值过滤（0.3）
  → 命中片段带来源标签交给模型
- **旁支**：检索前检查索引是否落后于档案更新时间，落后则重建

**图 6　数据模型与权限边界**

11 张表分三组画出，并标注权限：
- 业务表（7 张）：`pets`、`pet_media`、`pet_updates`、`applications`、
  `application_events`、`yard_administrators`、`yard_settings`
- 限频表（1 张）：`rate_limit_events`
- 向量表（2 张）：`knowledge_chunks`、`pet_photo_vectors`
- 权限标注三档：匿名可读 / 仅管理员 / 仅特权通道

**图 7　向量模型语义方向实测**

数据图，用真实测量值：

- 领养相关与无关句之间 **0.2566**

- 说明：相关相似度高于无关相似度，说明检索方向正确

## 任务二：排版成稿

### 输入

- `docs/技术文档-正文.md` —— 全部文案
- 你绘制的配图

正文里用 `> **【插入图 N】标题**` 标出图片位置，`> 图注：...` 给出图注。

### 输出

- `docs/成都猫狗小院-技术文档.docx`
- `docs/成都猫狗小院-技术文档.pdf`

### 排版规格

**页面**
- A4，页边距上下 2.5cm、左右 2.6cm
- 正文行距 1.5 倍，段后 0.3 行
- 页脚居中显示页码
- 每个一级标题（`# 一、二、三`）另起一页

**字体**
- 正文：微软雅黑 10.5pt
- 一级标题：微软雅黑加粗 18pt
- 二级标题：微软雅黑加粗 14pt
- 三级标题：微软雅黑加粗 12pt
- 代码与英文技术名词：Consolas 10pt
- **中文必须同时设置 `w:eastAsia` 字体**，只设 `font.name` 会导致中文回退

**表格**
- 三线表风格（顶线、表头下线、底线），不要满格网格
- 表头加粗 10pt，表格宽度不超过版心，每个表格上方给出表号与表名

**图片**
- 居中，宽度不超过版心，保持原始宽高比
- 图下方给图注，格式「图 N　名称」，9pt 居中

**封面与目录**
- 封面：文档标题、副标题（赛事名称与赛项主题）、线上地址、日期
- 封面后插入目录页

### 硬约束

**PDF 页数不得超过 30 页。** 赛事硬性要求，超了会影响评审。
排版完成后必须实测页数，超出时压缩行距、图片尺寸或调整分页，
**不要删减正文内容**。

**不得改动事实。** 可以润色语句、修正错别字、调整段落顺序，
但**不得新增任何技术细节**——正文里每一处技术描述都来自真实实现，
你没有项目上下文，凭想象补充的内容会是错的。
发现遗漏或前后矛盾，**标记出来交给写作方**，不要自行填补。

**不得出现真实密钥。** 任何形式的 API Key、机器人地址、密码都不得写入文档。

### 验收

自行检查并报告结果：

1. 转 PDF，读取页数，确认不超过 30 页
2. 逐页渲染成图片，检查：文字是否溢出表格或图片、是否有标题孤行、
   配图是否清晰且图注对得上、页码是否连续
3. 检查目录中的章节与实际一致
4. 报告最终页数与文件路径

**发现问题就修，修完重新渲染确认。不要只跑一遍就交付。**

## 参考：本机可用的工具链

如果环境与本机一致，DOCX 转 PDF 与逐页渲染可用内置 LibreOffice Kit：

```bash
node <libreoffice-kit>/lib/cli.js convert --input 文档.docx --output 文档.pdf
node <libreoffice-kit>/lib/cli.js render --input 文档.docx --output-dir preview --pages 1,2,3 --dpi 110
```

`render` 的返回里有 `pageCount`、每页图片路径与缺失字体信息。

Word 文档生成可用 `python-docx`。绘图工具由你自行选择。
如果环境不同，用你手上可用的方案，能达到同样效果即可。
