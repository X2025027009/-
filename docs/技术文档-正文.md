# 一、项目概述

## 1.1 项目背景

成都猫狗小院是真实在运营的私人流浪动物救助站。本项目的服务对象不是虚构场景，
小院每天在处理真实的领养咨询与申请。

平台的**基础版本**于 2026 年 9 月上线并投入使用，包含宠物档案展示、领养申请提交、
管理员后台、企业微信新申请提醒四项功能，由项目负责人独立开发完成。

本次参赛是在这个已经运行的平台之上做增量，不是从零搭建。

## 1.2 参赛期间的工作范围

参赛期间（2026 年 10 月起）的工作集中在两处：

**一是 AI 能力。** 把平台从「能收申请」推进到「能判断什么样的领养更可能成功」。
共实现六项 AI 能力，覆盖访客侧与管理员侧。

**二是工程质量。** 引入 ESLint 与 Prettier、补环境变量模板、补十三个验证脚本、
修复几处历史问题（包括一处导致后台多个功能长期不可用的缺陷）。

全部改动记录在仓库提交历史中，共 35 次提交，跨 29 天。

## 1.3 与赛项主题的关系

赛项主题是「健康守护」。流浪动物救助语境下的「健康」，不只指动物本人的身体状况，
更指向**领养关系本身的健康度**。

一次不匹配的领养，结果通常是二次遗弃。动物经历一次被领养再被退回，
伤害往往大于从未被领养。而绝大多数不匹配，在申请阶段其实是可以识别出来的——
租房没有经房东同意、家庭成员意见不一致、白天无人陪伴、居住地不适合养大型犬。

本项目做的是把这些问题**提前到申请之前和审核之中**发现。

## 1.4 名词约定

| 名词 | 含义 |
| --- | --- |
| 宠物档案 | 宠物的种类、性别、年龄、性格描述、健康状况、标签 |
| 领养要求 | 这只宠物对应的具体要求，如封窗、家庭成员同意 |
| 回访记录 | 领养后的跟踪记录，含日期、标题、正文 |
| 工具（Tool） | 模型可以主动调用的服务端函数，本项目共六个 |
| 向量检索 | 把文本或图片转成向量，按语义相似度而非关键词匹配 |
| 特权通道 | 云函数内部以表属主身份访问数据库的通道，绕过行级安全策略 |

# 二、需求分析

## 2.1 救助站的实际处境

小院目前只有**一位管理员**，负责全部宠物档案维护、申请审核、领养后回访。
申请在真实进来，每一条都要人工读完，再对照这只宠物的领养要求逐项核对。

这个处境决定了两条设计约束：

**约束一：AI 不能增加工作量。** 任何需要管理员额外维护数据、额外点击确认的设计都要排除。

**约束二：AI 不能替代判断。** 管理员的时间紧，但录取决定不能交给模型，
出错的社会成本由动物承担。

## 2.2 访客侧需求

**需求 1：不知道该选哪只。** 访客通常凭照片产生好感，但照片看不出是否适合自己。
现有的按种类、性别、状态筛选，只能表达"我要猫"，表达不了"我要一只不用天天遛的猫"。

**需求 2：描述性需求表达不出来。** 这是关键词筛选的根本局限。
当访客说「想找一只安静点的」，而档案里写的是「不爱动，大部分时间在睡觉」时，
关键词匹配返回空结果，但语义上它们是同一件事。

**需求 3：部分访客不擅长打字。** 小院的申请人群中包含年长申请人。
要求他们用文字描述居住情况、作息、家人态度，本身就是一道门槛。

## 2.3 管理员侧需求

**需求 4：逐条读申请耗时。** 一份正式申请包含姓名、年龄、性别、联系方式、
住房情况、养宠经验、家庭成员态度、现有宠物、补充说明。管理员需要从中提取要点，
再对照要求找缺口。

**需求 5：需要知道申请人是否重复投递。** 同一人在短时间内向多只宠物提交申请，
是一个值得注意的信号，但人工核对需要翻遍历史记录。

**需求 6：需要知道宠物此前的回访情况。** 判断一只宠物是否适合再次开放领养，
历史上的领养结果很重要。

## 2.4 非功能性需求

| 需求 | 说明 |
| --- | --- |
| 隐私保护 | 申请人提交的是个人信息，不得进入公开仓库、不得发给外部模型 |
| 成本可控 | 赛事要求使用商用 API 须自行承担费用，需控制在免费额度内 |
| 服务可用 | AI 服务异常不得影响领养申请提交这条核心业务 |
| 可维护 | 小院没有专职开发者，代码需要负责人自己能看懂、能长期维护 |
| 如实表达 | AI 不得编造档案里没有的信息，不得对未公布的政策作推测 |

## 2.5 明确不做的事

需求分析同样包括划定边界。以下四件事**明确不做**：

**不做录取决定。** AI 只做信息整理与提示，最终决定权在管理员。项目在提示词、
界面文案、系统提示三处都写明了这一点。

**不做内容生成。** 不生成宠物照片、不生成宣传文案。救助站的素材应当来自真实记录。

**不做社交功能。** 不引入评论、点赞、关注。平台的目的是促成领养，不是留住用户。

**不做视频分析。** 多模态只覆盖文本、图片、语音三种模态。视频与领养场景关联弱，
加入只是为了凑数。

# 三、系统架构设计

## 3.1 整体架构

> **【插入图 1】整体系统架构**
> 图注：平台由静态前端、两个云函数、PostgreSQL 数据库与对象存储组成。
> 两条请求链路相互独立，AI 服务异常不影响业务请求。

系统分为四层：

**前端层。** 单页应用，原生 JavaScript 与 CSS，无构建步骤。
通过 CloudBase 网关访问后端。

**业务后端。** 云函数 `yard-api`，Event 类型。负责申请提交、修改令牌校验、
后台管理接口、企业微信提醒。

**AI 后端。** 云函数 `ai-stream`，HTTP 类型。负责 SSE 流式对话、工具调用、
向量检索、图像比对。

**数据层。** PostgreSQL（CloudBase RDB）承载全部业务数据与向量数据，
对象存储承载宠物影像。

## 3.2 云函数拆分

> **【插入表 2】云函数职责划分**

| 云函数 | 类型 | 职责 | 超时 |
| --- | --- | --- | --- |
| `yard-api` | Event | 申请提交与修改、后台管理、企业微信提醒、管理员侧 AI 审核 | 15 秒 |
| `ai-stream` | HTTP | SSE 流式对话、工具调用、RAG 检索、以图搜宠 | 60 秒 |

**为什么 AI 必须单独一个函数。** 这不是架构偏好，是平台限制：
SSE 流式响应只在 HTTP（Web）类型的云函数上支持。
`yard-api` 是 Event 类型，经网关调用只返回一次性 JSON，无法边生成边推送。

拆分的附带收益是风险隔离。AI 服务涉及外部模型接口、向量服务、图像抓取，
不确定性高于业务逻辑。放在独立函数里，AI 出问题不影响申请提交这条主链路。

## 3.3 技术选型

### 3.3.1 前端：原生 JavaScript，不引入框架

**理由。** 站点是纯静态的，无构建步骤，复杂度和首屏体积都最低。
更重要的原因是可维护性：小院没有专职开发者，代码需要负责人自己能看懂。
引入构建工具链后，任何一次依赖升级、构建配置变更都可能让项目卡住，
而没有人能处理。

**代价。** 评分标准中「TypeScript 规范使用」「组件化架构设计」两项无法得分。
我们接受这个代价，把工程复杂度的预算集中投入到占权重 35% 的 AI 部分。
这个取舍在第七章创新点中会进一步说明。

### 3.3.2 数据库：PostgreSQL + 行级安全策略

**理由。** 权限不能依赖前端自觉。CloudBase RDB 支持 PostgreSQL 的行级安全策略（RLS），
可以把「谁能读哪一行」写在数据库里，前端即使被篡改也读不到不该读的数据。

项目实施中所有表均启用 RLS。例如 `yard_administrators` 表只对 `authenticated`
角色开放，且必须满足 `is_yard_admin()` 判定；匿名用户可以读宠物档案，
但没有对任何业务表的写权限。

### 3.3.3 向量检索：pgvector

**理由。** 数据库原生支持向量类型与近似最近邻索引，不需要额外引入向量数据库。
数据规模在数百到数千条量级，单库即可承载，运维成本最低。

**维度选择。** pgvector 的近似最近邻索引（HNSW、IVFFlat）对 `vector` 类型
只支持 2000 维以内。这一限制直接决定了两处选型：

- 文本向量选择 `kinfra-text-embedding-0.6b`（1024 维），可以建立 HNSW 索引。
  质量更高的 4b 模型输出 2560 维，超出索引上限，规模增大后只能全表精确扫描，
  反而更慢。
- 图片向量模型 `kinfra-vl-embedding-2b` 固定输出 2048 维，同样超出 `vector` 的
  索引上限。这里改用 `halfvec`（半精度，索引上限 4000 维）承接，
  代价是极小的精度损失，换来可以走索引检索。

### 3.3.4 模型服务：两个供应商分工

| 用途 | 服务 | 模型 |
| --- | --- | --- |
| 对话与工具调用 | DeepSeek | `deepseek-chat` |
| 文本向量 | 腾讯云 TokenHub | `kinfra-text-embedding-0.6b` |
| 图片向量 | 腾讯云 TokenHub | `kinfra-vl-embedding-2b` |
| 图片理解 | 腾讯云 TokenHub | `hy-vision-2.0-instruct` |

**为什么对话与向量分开。** DeepSeek 提供对话能力，但不提供向量化接口。
向量化需要另外的服务。选择腾讯云 TokenHub 的原因是它与现有云资源同源，
凭证与网络链路最短；同时它一个模型同时覆盖文本向量与图片向量，
不需要为多模态再引入第二个供应商。

## 3.4 数据模型

> **【插入图 6】数据模型与权限边界**
> 图注：业务表与向量表的权限边界。向量表不对外开放，仅供云函数经特权通道访问。

项目共 11 张表，按用途分为三类：

**业务表。** `pets`（宠物档案）、`pet_media`（影像）、`pet_updates`（回访记录）、
`applications`（领养申请）、`application_events`（状态变更记录）、
`yard_administrators`（管理员）、`yard_settings`（站点设置）。

**限频表。** `rate_limit_events`，记录限频事件。IP 只以 SHA-256 哈希形式存储。

**向量表。** `knowledge_chunks`（文本向量，1024 维）、
`pet_photo_vectors`（图片向量，2048 维）。

向量表启用 RLS 且不建立任何策略，同时回收了 `anon` 与 `authenticated` 的授权。
这意味着客户端无法直接读取。云函数经特权通道访问，不受 RLS 限制。

## 3.5 数据访问的两条通道

> **【插入图 4】数据访问的两条通道**
> 图注：前端直连数据库受 RLS 约束；云函数经特权通道访问，可读写受限表。

这是本项目最重要的一处工程决策，也是**一次真实缺陷的产物**。

**通道一：前端直连。** 前端通过 CloudBase SDK 直接访问数据库。
读到的数据由 RLS 策略决定，写操作同样受策略约束。
用于读取公开宠物档案、公开站点设置，以及管理员读取申请列表。

**通道二：云函数特权通道。** 云函数通过腾讯云 OpenAPI 的 `ExecutePGSql` 接口
执行 SQL，以表属主身份运行，绕过 RLS。
用于所有需要写入或读取受限数据的场景。

**为什么必须分开。** 云函数内部的 `@cloudbase/node-sdk` 提供的 `rdb()` 客户端
以**匿名身份**运行，而匿名角色在这些表上没有授权。项目在开发过程中把
`requireAdmin` 与管理类操作写在了 `rdb()` 上，导致后台的申请审核、宠物档案保存、
收件箱读取等功能**长期不可用**，报错为 `permission denied for table`。

这个问题一直没有暴露，直到新增删除功能时才被撞出来——因为它只在真正调用到
那些功能时才会出现，而此前从未被测试覆盖。

修复方式是把这些操作全部迁移到特权通道。当前项目的规则是：
**云函数内需要访问受限数据时必须使用特权通道，不得使用 `rdb()`**。
